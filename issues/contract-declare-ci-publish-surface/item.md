# contract under-declares the release surface: no homebrew target, and cargo-publish contradicts the CI-publish policy

## Description

## Description

This repo's contract **under-declares its release surface**, and the two engine features
that would let it declare the truth have now shipped.

Current state:

```yaml
targets:
  - {ecosystem: rust, package: glasspad, registry: crates.io,   adapter: cargo-publish}
  - {ecosystem: rust, package: glasspad, registry: gh-releases, adapter: cargo-dist}
```

Two things are wrong with that.

**1. The Homebrew channel is invisible.** `dist-workspace.toml` carries
`installers = ["shell", "homebrew"]` and `publish-jobs = ["homebrew"]`, so cargo-dist
writes `jarimustonen/homebrew-glasspad` on every tag. The contract does not mention it,
so the engine neither plans for it nor verifies it — a channel real users install from is
outside the tool's field of view. Declaring it as `adapter: homebrew-tap` was **not** an
option before, because that would have made the engine write the same formula cargo-dist
already writes (see issuectl's `homebrew-double-writer-contract` for what that costs).

**2. `cargo-publish` is wrong for this repo.** This repo's own operating policy forbids a
local `cargo publish` — the local credentials may be stale (403) and the CI token in
`publish-crates.yml` is the source of truth. `adapter: cargo-publish` tells the engine to
publish locally, which is exactly what must not happen. This is why the 0.4.0 cut had to
abandon the engine and fall back to the manual tag recipe.

## Fix

```yaml
targets:
  - {ecosystem: rust, package: glasspad, registry: crates.io,   adapter: cargo-publish-ci}
  - {ecosystem: rust, package: glasspad, registry: gh-releases, adapter: cargo-dist}
  - {ecosystem: rust, package: glasspad, registry: homebrew,    adapter: cargo-dist}
distribution:
  adapter: cargo-dist
  gh_releases: true
  installers: [shell, homebrew]
  homebrew_tap: jarimustonen/homebrew-glasspad
  platforms:
    - aarch64-apple-darwin
    - aarch64-unknown-linux-musl
    - x86_64-unknown-linux-musl
```

`cargo-publish-ci` makes the cut stop at the pushed tag: the engine runs its gates, bumps,
tags, and pushes, then CI publishes and the engine **observes** the result on the registry
index rather than publishing itself.

## Before the first engine cut, check two things

- **`publish-crates.yml` must be tag-triggered and actually run `cargo publish`.** The
  engine does not yet preflight this (ossctl `delegated-publish-workflow-preflight`), so a
  renamed or `workflow_dispatch`-only workflow means a pushed tag followed by a 20-minute
  wait for a publish nobody performs.
- **This is a single-crate repo.** `release --bump` could not bump a plain
  `[package] version` manifest at all until ossctl 0.8.0; make sure you are on 0.9.0+.

## Reference: a correctly-declared contract

`ossctl`'s own `OSS-RELEASE.md` is the worked example of a **fully-declared release
surface** — every channel the repo actually ships on appears as a target, plus a
`distribution:` block that matches its `dist-workspace.toml`:

```yaml
targets:
  - {ecosystem: rust, package: ossctl-core, registry: crates.io,   adapter: cargo-publish}
  - {ecosystem: rust, package: ossctl,      registry: crates.io,   adapter: cargo-publish}
  - {ecosystem: rust, package: ossctl,      registry: gh-releases, adapter: cargo-dist}
  - {ecosystem: rust, package: ossctl,      registry: homebrew,    adapter: homebrew-tap}
distribution:
  adapter: cargo-dist
  gh_releases: true
  installers: [shell]
  homebrew_tap: jarimustonen/homebrew-ossctl
  platforms:
    - aarch64-apple-darwin
    - aarch64-unknown-linux-musl
    - x86_64-unknown-linux-musl
```

**Copy the SHAPE, not every adapter.** ossctl deliberately differs on one line, and
copying it would recreate the bug this issue is about:

| | ossctl | this repo |
|---|---|---|
| `dist-workspace.toml` | `installers = ["shell"]`, **no** `publish-jobs` | `installers = [..., "homebrew"]`, `publish-jobs = ["homebrew"]` |
| who writes the tap | the ossctl engine, in its `dist` phase | **cargo-dist's CI job**, on every tag |
| correct homebrew adapter | `homebrew-tap` (engine-owned) | **`cargo-dist`** (CI-delegated) |

The engine-owned formula carries a first-line marker
(`# Generated by ossctl; do not edit by hand`); a CI-written one does not, and must not
be required to. That is why the adapter has to say who the writer is.

Fleet context and the full per-repo audit:
`homebase/issues/cross-repo-release-standardisation/audit-2026-08-17.md`.

## Target state: the fleet ships uniformly

All four public fleet repos (`issuectl`, `glasspad`, `orchestratectl`, `project-canon`)
should end up with the same declared shape, since all four already carry
`publish-jobs = ["homebrew"]` and their own `publish-crates.yml`:

```yaml
targets:
  - {ecosystem: rust, package: <core>, registry: crates.io,   adapter: <cargo-publish | cargo-publish-ci>}
  - {ecosystem: rust, package: <bin>,  registry: crates.io,   adapter: <cargo-publish | cargo-publish-ci>}
  - {ecosystem: rust, package: <bin>,  registry: gh-releases, adapter: cargo-dist}
  - {ecosystem: rust, package: <bin>,  registry: homebrew,    adapter: cargo-dist}
distribution:
  adapter: cargo-dist
  gh_releases: true
  installers: [shell, homebrew]
  homebrew_tap: <tap>
  platforms: [aarch64-apple-darwin, aarch64-unknown-linux-musl, x86_64-unknown-linux-musl]
```

`intakectl` is the deliberate exception: it publishes nothing and uses `targets: []`.
`ossctl` is the other exception: it keeps the engine-owned tap, since it is the only
live exercise of that path.

## Required tool version

`ossctl 0.9.0` or newer. The CI-delegated homebrew adapter shipped in 0.8.0 and the
`cargo-publish-ci` adapter in 0.9.0. Check with `ossctl --version` (which also only
started working in 0.8.0).
